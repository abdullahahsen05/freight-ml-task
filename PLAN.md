## 3. Implementation principles

### 3.1 Preserve and validate inputs

Before reorganizing anything:

- Compute hashes for all supplied files and save them to `artifacts/manifests/input_hashes.json`.
- Preserve untouched input CSVs under `data/raw/` or keep originals in place and copy them there.
- Keep the supplied `score.py` behavior unchanged. If formatting or comments are changed, retain an exact original copy and prove equivalent behavior. Prefer not to edit it.
- Build schema validators that check required columns, dtypes that can be coerced safely, row counts, ID uniqueness, date parseability, and target presence/absence.

### 3.2 Build a code pipeline, not a notebook dependency

Notebooks may be created for optional exploration, but all required outputs must come from importable Python modules and CLI commands. A single command should be sufficient, for example:

```bash
python scripts/run_pipeline.py --config configs/default.yaml
```

or:

```bash
python -m freight_rate_ml.pipeline --project-root .
```

The command must:

1. validate inputs
2. perform/load EDA summaries
3. run model comparison or load a reproducibly selected configuration
4. train final models
5. generate both prediction files
6. run output validators
7. run `score.py`
8. generate the report
9. run final artifact checks

A faster `--skip-search` or `--reuse-artifacts` option is acceptable after the full run exists, but the README must identify which command performs a clean reproduction.

### 3.3 Separate training, selection, and final inference

Avoid a monolithic script. Keep explicit boundaries:

- Data contract and loading
- Fold creation
- Feature engineering
- Preprocessing
- Candidate construction
- Training and prediction
- Metric calculation
- Artifact serialization
- Report generation

All transformations learned from data must fit on training folds only during cross-validation.

## 5. Feature-engineering plan

Implement feature generation as deterministic functions usable identically in training, validation, and December prediction.

### 5.1 Raw features to retain

Retain or safely transform:

- pickup and delivery names
- pickup and delivery latitude/longitude
- distance
- equipment
- weight
- date
- market index
- quote signal

Exclude `load_id` from predictive features. Exclude `posted_rate` from all feature matrices.

### 5.2 Date features

Generate, as appropriate:

- year
- month
- day of month
- day of week
- day of year
- week of year
- quarter
- weekend flag
- days since first labeled date
- cyclical sine/cosine features for day of week and annual seasonality

Do not use raw integer date ordering without also considering nonlinear/seasonal representation.

### 5.3 Geography and lane features

Generate robust features that generalize to unseen names:

- exact route key (`pickup -> delivery`) for models that can handle unseen categories
- unordered city pair if useful
- same-city flag
- latitude difference
- longitude difference
- absolute latitude/longitude differences
- haversine or geodesic distance from coordinates
- supplied-distance / geodesic-distance ratio with safe handling
- route direction/bearing components if they improve validation
- origin/destination region or coordinate bins learned without external APIs, if useful
- pickup and delivery frequency counts learned on each training fold only

Do not leak target encodings across folds. If target encoding is used, it must be out-of-fold for training rows and have safe priors for unseen categories.

### 5.4 Weight features

Benchmark and choose a fold-safe strategy:

- `weight_abs`
- `weight_was_negative`
- `weight_was_missing`
- clipped or winsorized weight based on training-fold bounds, if validated
- weight per mile or load-density interaction, if useful

Keep the original raw sign only as a diagnostic; do not allow invalid negatives to silently act as normal physical weights without analysis.

### 5.5 Market and quote interactions

For the full-feature validation model, consider:

- missingness flags
- quote signal x distance
- market index x distance
- quote signal x market index
- equipment interactions
- date-relative market features that are available at inference

Do not overfit hand-created interactions when tree models learn them naturally; retain only features supported by temporal validation.

### 5.6 Prediction safety

Final predictions must be finite and positive. Apply a defensible lower bound derived from the training target, such as a small positive floor, only after model prediction. Any upper clipping must be justified by fold results and documented. Never use arbitrary hardcoded rates.

## 6. Validation design

### 6.1 Required primary validation

Implement chronological, out-of-time evaluation. Preferred structure:

- Multiple expanding-window folds, each trained only on dates earlier than its validation dates
- Validation horizons of approximately 30-61 days where sample size permits
- A final recent fold that approximates the actual future horizon

A possible starting design is:

1. Train through June; validate July
2. Train through July; validate August
3. Train through August; validate September
4. Train through September; validate October

Also evaluate a longer final holdout, such as training through August and validating September-October, to mimic the two-month final horizon. Adapt exact cutoffs after inspecting row counts, but preserve chronology.

Record fold dates and row counts in `artifacts/metrics/folds.csv`.

### 6.2 Secondary diagnostics

Optional secondary checks:

- grouped splits by route to test unseen-route robustness
- metrics on rows whose pickup, delivery, or route is unseen relative to the fold training set
- random split only as a diagnostic to quantify how optimistic it is

Do not choose the final model based only on a random split.

### 6.3 Metrics

For every candidate and fold, save:

- MAE
- RMSE
- R-squared
- median absolute error
- WAPE and/or guarded MAPE
- fit time
- prediction time
- normal-tail and extreme-tail metrics
- seen-route versus unseen-route metrics where applicable

Save long-form results to `artifacts/metrics/model_results.csv` and aggregated rankings to `artifacts/metrics/model_rankings.csv`.

Primary ranking is mean temporal MAE. Use the tie-break policy in `CONTEXT.md`.

## 7. Model-development plan

### 7.1 Baselines

Implement meaningful baselines before advanced models:

1. Global median rate
2. Distance-based linear baseline
3. Median rate-per-mile by equipment, with global fallback
4. A regularized linear model on engineered numeric and encoded categorical features

Baselines establish whether advanced models add real value and catch pipeline errors.

### 7.2 Serious candidates

Evaluate at least two strong nonlinear candidates in addition to baselines. Recommended:

- CatBoostRegressor with categorical features and robust loss options
- LightGBM or HistGradientBoosting/RandomForest/ExtraTrees pipeline with explicit encoding
- Optional XGBoost if it adds measurable value without unnecessary complexity

CatBoost is especially suitable for mixed numerical/categorical data and unseen-category fallback, but it must still be validated against geographic-only generalization. LightGBM or another candidate provides a useful independent inductive bias.

For each strong candidate, compare a limited, purposeful set of variations:

- raw target versus `log1p(target)`
- MAE/Huber/RMSE-style objectives where supported
- full categorical plus geographic features versus reduced memorization features
- missing/negative weight treatments
- native missing handling versus explicit imputation

Do not launch an uncontrolled grid search. Use a small deterministic search or Bayesian/random search with bounded trials and time. The search space and chosen seed must be recorded.

### 7.3 Model selection and optional ensemble

Select the model using aggregate temporal MAE and the defined tie-breakers. Then evaluate a simple weighted average of the top two diverse models. Select the ensemble only if it improves temporal validation consistently, especially on the recent fold, and remains reproducible.

Save:

- candidate configurations
- fold metrics
- selected configuration
- feature list
- model artifact(s)
- preprocessing artifact(s)

Use `joblib`, native model serialization, or another stable format.

### 7.4 Error analysis

For the selected candidate, produce:

- residual distribution
- residual versus distance
- errors by equipment
- errors by month/fold
- errors by distance band
- errors by seen/unseen city or route
- top absolute-error examples with identifiers and features
- performance with and without extreme target rows

Use this analysis to make one final constrained improvement pass. Do not endlessly tune.
